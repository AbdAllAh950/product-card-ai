# AI-помощник для карточек товаров КИП

Прототип сервиса для B2B-магазина контрольно-измерительных приборов: по данным о приборе (JSON или веб-форма) готовит черновик карточки товара для контент-менеджера.

Для каждого товара сервис возвращает:

- SEO-заголовок до 70 символов;
- SEO-описание на 800–1 200 символов;
- таблицу ключевых характеристик;
- 3–5 поисковых запросов;
- блок для менеджера: кому подходит прибор, какие задачи решает, аргументы для клиента;
- список того, чего не хватает во входных данных.

Главное требование задания — не выдумывать характеристики. Поэтому таблицу характеристик строит код, а тексты модели проходят две проверки. Первая — детерминированная: каждое число и каждый «рискованный» термин (ГОСТ, взрывозащита, интерфейсы, гарантия, оценки вроде «долговечный» и т. п.) должны быть во входных данных. Вторая — модель-фактчекер: она сверяет с данными утверждения без чисел. Всё, что не подтвердилось, модель исправляет, а если не смогла — код удаляет фразу и пишет замечание.

Модель — любая с OpenAI-совместимым API: YandexGPT (Yandex AI Studio), OpenAI, DeepSeek или локальная модель через Ollama. Меняются только переменные окружения.

## Быстрый старт

Нужен Python 3.11+.

```bash
git clone https://github.com/AbdAllAh950/product-card-ai.git
cd product-card-ai
python3 -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env                                  # впишите ключ и модель
```

Пример `.env` для Yandex AI Studio:

```env
LLM_BASE_URL=https://ai.api.cloud.yandex.net/v1
LLM_API_KEY=<API-ключ AI Studio>
LLM_PROJECT=<id каталога>
LLM_MODEL=gpt://<id каталога>/aliceai-llm        # или .../yandexgpt/latest
```

Другие провайдеры описаны в [`.env.example`](.env.example). Ключ хранится только в `.env`, а `.env` добавлен в `.gitignore`.

### Командная строка

```bash
# карточка в консоль (Markdown)
python -m app.cli examples/input/tm-510r-m2.json

# оба товара сразу: для каждого сохраняются .md и .json
python -m app.cli examples/input/*.json --out examples/output

# только JSON
python -m app.cli examples/input/pd100-di1.6-111-0.5.json --format json
```

Коды выхода: `0` — успех, `2` — ошибка во входных данных, `3` — ошибка модели или API.

### Веб-форма и API

```bash
uvicorn app.web:app --reload
```

- http://127.0.0.1:8000 — форма: вставьте JSON или заполните поля (характеристики по одной на строку, «параметр: значение»). Результат выводится в Markdown и JSON с кнопками «Копировать».
- `POST /api/card` — тело запроса: JSON товара. Ответ: `{"card": {...}, "markdown": "..."}`. Некорректный JSON → `400` с понятным текстом ошибки, ошибка модели → `502`.

```bash
curl -s -X POST http://127.0.0.1:8000/api/card \
  -H 'Content-Type: application/json' \
  --data-binary @examples/input/tm-510r-m2.json
```

## Входные данные

```json
{
  "name": "Манометр ТМ-510Р.00 (0–10 кгс/см2) G1/2 М2",
  "manufacturer": "РОСМА",
  "specs": {
    "диапазон измерений": "0–10 кгс/см2",
    "класс точности": "1,5",
    "диаметр корпуса": "100 мм"
  },
  "description": "Манометры в стандартном исполнении применяются для измерения избыточного давления…",
  "sku": "109811",
  "source_url": "https://www.souz-pribor.ru/product/tm-510r-m2/"
}
```

- Обязательно только `name`. Если остальных полей нет, карточка всё равно строится, а недостающее попадает в блок «Требует уточнения» и в таблицу со значением «данных нет».
- `specs` можно передать объектом `{"параметр": "значение"}` или списком `[{"name": "...", "value": "..."}]`.
- `sku`, `source_url` и `category` — служебные поля. Они попадают в метаданные результата, но в модель не передаются (кроме `category`).

Товары для примеров взяты с souz-pribor.ru. Данные собраны со страниц товаров, потому что в YML-фиде магазина есть только название, тип, производитель и артикул, а характеристик и описания нет (см. раздел «Импорт из фида»):

- [`examples/input/tm-510r-m2.json`](examples/input/tm-510r-m2.json) — манометр РОСМА ТМ-510Р М2;
- [`examples/input/pd100-di1.6-111-0.5.json`](examples/input/pd100-di1.6-111-0.5.json) — датчик давления ОВЕН ПД100-ДИ1,6-111-0,5;
- [`examples/input/incomplete-from-feed.json`](examples/input/incomplete-from-feed.json) — неполные данные, чтобы показать отметки «данных нет».

### Что выяснилось на реальных ответах модели

Эти случаи встретились при прогонах на Alice AI LLM и закрыты в коде:

1. **Потерянные имена ключей JSON.** Модель возвращала `{"seo_title": "…", ",": "<всё описание>", …}`, а в блоке менеджера — `", ": "<кому подходит>"`. В результате поля оказывались пустыми; в одном из прогонов пустые поля пришли трижды подряд, и карточка манометра не собралась. Теперь ключ без букв сопоставляется с первым недостающим ключом схемы того же типа, а в `meta.keys_repaired` записывается, что было восстановлено.
2. **«Расшифровка» кодов.** Модель написала, что IP40 «гарантирует защиту от пыли и брызг воды». Это неверно: вторая цифра 0 означает, что защиты от воды нет. Фраза удалена проверкой, а в промпт добавлен запрет толковать коды и материалы своими словами.
3. **«Вода» при скудных данных.** Чтобы набрать 800 символов, модель дописывала общие фразы («…для предотвращения аварийных ситуаций»). Теперь для товаров с малым количеством данных длину не добирают: описание остаётся коротким, и код ставит замечание.
4. **Ложные срабатывания фактчекера.** Модель-фактчекер помечала как неподтверждённые дословные цитаты из описания, причём без причины. Из-за этого после исправления пропадала верная область применения. Теперь отметка учитывается, только если указана причина и утверждение заметно расходится с лексикой данных: меньше 80 % основ его слов встречаются во входных данных. На реальных примерах дословные цитаты получают 1,0, а выдумки вроде «мембрана устойчива к воздействию рабочей среды» — 0,78.
5. **Пропущенная область применения.** Модель писала «область применения не указана», хотя она была в описании. Промпт уточнён: если область применения, системы или заказчики названы в данных, их нужно перечислить.

## Как устроено

```
JSON / форма
   │
   ▼
input_check  ── некорректный JSON или нет name → понятная ошибка
   │            пустые поля, нет описания → «Требует уточнения»
   │            чек-лист по типу прибора → «данных нет» в таблице
   ▼
prompts ─► LLM (OpenAI-совместимый API, temperature 0.2, JSON-режим)
   │
   ▼
проверки ── длина заголовка и описания, 3–5 запросов,
   │        числа и термины, которых нет во входных данных
   │   └─ есть проблемы → модель получает их список и исправляет (до 2 раз)
   ▼
фактчекер ── модель сверяет утверждения без чисел с данными
   │   └─ есть неподтверждённые → одно исправление и повторная проверка
   ▼
финальная страховка ── фразы с непроверенными данными удаляются,
   │                   о каждом удалении пишется замечание
   ▼
карточка: JSON + Markdown
```

### Решения, которые не дают выдумывать характеристики

1. **Характеристики строит код, а не модель.** Таблица собирается из `specs` как есть: значения не переписываются, единицы не пересчитываются. Если для типа прибора обычно указывают параметр, а в данных его нет, в таблице стоит «данных нет».
2. **Промпт задаёт один источник фактов.** Модель получает только поля товара в виде JSON и прямой запрет добавлять числа, стандарты, сертификаты, исполнения, гарантию, цены и отрасли. Ей также передаётся список характеристик, которых нет в данных, с указанием не называть их значения.
3. **Автоматическая проверка каждого текста.** Все числа ответа сравниваются с числами входных данных: «1,5» и «1.5», «500 000» и «500000» считаются одним числом. Пересчёт «10 кгс/см2 → 0,98 МПа» поэтому тоже ловится: 0,98 в данных нет. Отдельно проверяется список «рискованных» терминов: ГОСТ, ТР ТС, сертификат, взрывозащита, Госреестр, RS-485/Modbus/HART, IP, гарантия, кислород и др. Если термин есть в ответе, но не во входных данных, это ошибка.
4. **Цикл исправления.** Найденные проблемы (числа, термины, длины, количество запросов) отправляются модели списком: «исправь только это». Если очередной ответ хуже предыдущего, в карточку идёт лучший.
5. **Страховка вместо доверия.** Если после двух исправлений проблема осталась, код удаляет предложение или пункт с непроверенными данными, а SEO-заголовок заменяет названием товара. Об этом пишется замечание, так что контент-менеджер видит, что поменялось.
6. **Фактчекер для утверждений без чисел.** «Мембрана устойчива к коррозии» не содержит ни чисел, ни терминов из списка. Такие фразы проверяет второй запрос к модели: она получает данные и пронумерованные утверждения и возвращает неподтверждённые с причиной. Выключается через `LLM_VERIFY=0`.
7. **Устойчивость к формату ответа.** JSON извлекается из markdown-блока, обёртка `{"card": {...}}` снимается, потерянные имена ключей восстанавливаются, проблемы формата отправляются модели на исправление.

### Промпты

Полный текст — в [`app/prompts.py`](app/prompts.py).

- **Системный промпт:** роль контент-менеджера B2B-магазина КИП; главное правило — только факты из «ДАННЫХ О ТОВАРЕ»; запрет пересчитывать единицы и приписывать модификации свойства всей серии; деловой стиль без превосходных степеней.
- **Пользовательский промпт:** JSON товара, тип прибора, список недостающих характеристик и схема ответа с ограничениями для каждого поля (≤ 70 символов, 800–1 200 символов, 3–5 запросов в нижнем регистре, аргументы для менеджера опираются на конкретные значения). Если область применения не указана, модель должна написать «Область применения в исходных данных не указана».
- **Промпт исправления:** список найденных проблем и требование «если не хватает фактов, лучше убери фразу, чем добавляй новое».
- **Промпт фактчекера:** данные товара и пронумерованные утверждения. Перефразирование и очевидное назначение прибора считаются подтверждёнными, а новые свойства, оценки, следствия и области применения — нет. Причина обязательна.

### Обработка ошибок

| Ситуация | Что происходит |
|---|---|
| Некорректный JSON | `Некорректный JSON: … (строка N, позиция M)`, CLI → код 2, API → 400 |
| Нет `name`, корень не объект, `specs` не того типа | понятное сообщение без обращения к модели |
| Пустые поля, нет описания, пустое значение характеристики | карточка строится, недостающее отмечено «данных нет» и в «Требует уточнения» |
| Нет ключа API | ошибка до запроса |
| 401/403 | сообщение о ключе, без повторов |
| 429, 5xx, таймаут, сетевая ошибка | повторы с паузой (`LLM_MAX_RETRIES`) |
| Провайдер не поддерживает JSON-режим | повтор без `response_format`, JSON задаётся промптом |
| Модель вернула не JSON или JSON в markdown-блоке | JSON извлекается из ответа, иначе повторный запрос |
| Ключи JSON потеряны или ответ обёрнут | ключи восстанавливаются, обёртка снимается; если не вышло — модели сообщается, какие ключи пришли |
| Фактчекер недоступен или вернул не JSON | карточка всё равно строится, в замечаниях — просьба проверить блок менеджера вручную |

## Импорт из фида

```bash
python -m app.feed feed.xml --search "ПД100-ДИ1,6-111-0,5" > product.json
python -m app.cli product.json
```

`app/feed.py` потоково читает YML-фид (47 978 товаров, 37 МБ) и делает из нужного товара заготовку входного JSON. В фиде souz-pribor.ru нет характеристик и описаний, поэтому карточка по одной заготовке честно состоит в основном из «данных нет». Это нормальный результат: сервис не дописывает то, чего нет в данных.

## Ограничения и что можно улучшить

- **Фактчекер — тоже модель.** Он может пропустить выдумку или ошибиться, поэтому его отметки фильтруются эвристикой (обязательная причина + лексическое расхождение). Надёжнее было бы требовать цитату-доказательство из данных для каждого утверждения или использовать NLI-модель.
- **Стоимость.** Обычно на карточку уходит 2 запроса (генерация + фактчекер), в худшем случае 6. Для каталога в десятки тысяч товаров стоит кешировать результаты и пропускать проверку для полностью табличных товаров.
- **Числа, написанные словами** («два года»), пока не проверяются.
- **Чек-листы есть для 4 типов приборов**: манометр, датчик давления, термопреобразователь, газоанализатор; для остальных используется общий список. Их стоит расширить по дереву категорий каталога.
- **Длина описания.** Если данных мало, описание честно получается короче 800 символов и помечается замечанием, а не добирается «водой».
- **Источник данных.** Данные для примеров собраны со страниц товаров вручную. Дальше можно добавить парсер страницы товара и PDF-паспортов, а для сканов — OCR.
- **Масштаб.** Для каталога нужны пакетная обработка фида с очередью и кешем, а также подбор поисковых запросов по реальной частотности (например, Wordstat).
- **Качество.** Стоит собрать оценочный набор из 30–50 товаров и следить за метриками: доля карточек без замечаний, среднее число попыток, доля удалённых фраз.

## Структура

```
app/
  input_check.py   разбор и проверка входных данных
  checklist.py     типы приборов и обязательные для них характеристики
  prompts.py       системный промпт, схема ответа, промпт исправления
  llm.py           клиент OpenAI-совместимого API: повторы, таймауты, ошибки
  grounding.py     проверка чисел и терминов по входным данным
  generator.py     цикл генерации, проверки, фактчекер, страховка, сборка карточки
  render.py        Markdown
  cli.py           командная строка
  web.py           веб-форма и JSON API (FastAPI)
  feed.py          заготовка входного JSON из YML-фида
examples/input     данные двух товаров и пример неполных данных
examples/output    сгенерированные карточки (.md и .json), raw/ — сырые ответы модели
tests/             pytest
```
